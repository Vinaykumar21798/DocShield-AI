Yes, masking affects the detection pipeline, but it does **not** modify the original document text.

In this codebase, masking means: “this character span has already been confidently claimed by a detector.” The original text stays intact in `MaskManager.original_text`; masked positions are only replaced with spaces in `remaining_text()` for routing/remaining-candidate logic. See `modules/detection/mask_manager.py`.

How it affects the pipeline:

1. **High-confidence entities are masked**
   In `PipelineState.add_entities()`, entities are added to `resolved_entities`, but only entities with confidence above the configured threshold are sent to `mask_manager.add_entities()`.

   Default threshold is `0.80` from `DynamicDetectionConfig`.

2. **Low-confidence entities are not masked**
   That allows another detector, especially Qwen, to inspect the same span later and possibly improve the result. This is tested in `tests/test_eob_pipeline.py`.

3. **Masking controls unresolved candidate detection**
   `remaining_candidate_summary()` scans `state.current_text`, which is the masked text. So once a high-confidence span is masked, it stops appearing as an unresolved candidate.

4. **Qwen is affected the most**
   Qwen runs only on unresolved/low-confidence contexts. Since Qwen contexts are built from masked remaining text, high-confidence masked spans are usually not sent to Qwen again.

5. **Original text is still used for persistence and redaction**
   The workflow saves the final detected entities into the DB in `_store_detection_results()`, then later `_apply_redactions()` replaces original source spans with `[REDACTED_ENTITY_TYPE]`. That is separate from detection masking.

Important nuance in the current implementation: for non-Qwen detectors, `_execute_dynamic_orchestration()` calls `_run_detector(..., custom_text=state.original_text, allow_claimed_spans=True)`. So Regex, Presidio, MedSpaCy, and GLiNER still run on the original text, not only the masked text. Exact duplicate spans are handled by `_matches_previous_entity()`, and final overlaps are handled later by deduplication/overlap resolution.

So the correct answer is: **masking does affect the pipeline, but it does not break it or redact early. It mainly prevents already confident spans from being treated as unresolved work, reduces duplicate/extra Qwen calls, and lets low-confidence spans continue to later detectors.**

Yes, that can happen, but in this codebase it mainly affects **Qwen/LLM**, not all NER models equally.

Current behavior:

- `MaskManager` replaces masked spans with spaces in `remaining_text()` while keeping `original_text` unchanged: [mask_manager.py](./modules/detection/mask_manager.py:32)
- High-confidence entities are masked inside `PipelineState.add_entities()`: [pipeline_state.py](./modules/detection/pipeline_state.py:171)
- Remaining candidates are found from `state.current_text`, meaning masked spans are invisible to later candidate routing: [pipeline_state.py](./modules/detection/pipeline_state.py:221)

But important: in the current orchestration, Regex/Presidio/MedSpaCy/GLiNER are run with `custom_text=state.original_text` and `allow_claimed_spans=True`: [service.py](./modules/detection/service.py:746). So those NER-style detectors still see the full original text during detection.

The bigger context-loss risk is Qwen. Qwen contexts are built from `state.current_text`, which is the masked version: [service.py](./modules/detection/service.py:821). So if a high-confidence entity near the unresolved span was masked, Qwen receives spaces instead of that neighboring context.

Example:

```text
Patient John Doe was prescribed Metformin 500mg.
```

If `John Doe` is already high-confidence and masked, Qwen may later see something closer to:

```text
Patient          was prescribed Metformin 500mg.
```

That may be fine for detecting medication/dosage, but it can hurt cases where the missing entity depends on nearby identity/context.

So the correct conclusion is:

**Yes, masking can remove useful context for LLM recovery and candidate routing. The code reduces duplicate detections, but the tradeoff is possible context loss around already-masked high-confidence spans. For the main NER detectors, the current code mostly avoids this by passing original text; for Qwen, the risk is real.**

A better future design would be to pass placeholders instead of blank spaces, for example `[MASKED_PATIENT]`, so Qwen still understands the document structure without re-detecting the exact value.

> so what,s the solution ?

Best solution: **do not remove masking**, change how Qwen receives context.

Masking is useful for avoiding duplicates. The problem is that Qwen gets blanked text, so it may lose nearby meaning. I’d solve it like this:

1. Keep the current mask for routing/deduplication.
2. For Qwen only, build context from the **original text window**.
3. Inside that Qwen context, replace already-detected high-confidence spans with typed placeholders instead of spaces.

Example current Qwen context:

```text
Patient          was prescribed Metformin 500mg.
```

Better Qwen context:

```text
Patient [MASKED_PATIENT] was prescribed Metformin 500mg.
```

This preserves useful semantic context without exposing the exact already-detected value.

The safest implementation would be in:

- [mask_manager.py](./modules/detection/mask_manager.py:32)
- [pipeline_state.py](./modules/detection/pipeline_state.py:245)
- [service.py](./modules/detection/service.py:776)

Important detail: if placeholders change text length, Qwen’s returned `start_char` / `end_char` offsets may no longer match the original document. So the clean solution is either:

1. Maintain an offset map from Qwen-context positions back to original positions.
2. Or pass original-text snippets to Qwen but also include a `known_masked_entities` metadata list like:

```json
[
  {"type": "PATIENT", "start": 8, "end": 16}
]
```

My recommendation: **use original context + typed metadata, not inline placeholders**, because it avoids offset bugs.

So Qwen prompt/context becomes:

```text
Input Text:
Patient John Doe was prescribed Metformin 500mg.

Already detected high-confidence spans:
- PATIENT at chars 8-16

Task:
Extract only unresolved PII/PHI entities. Do not return already detected spans.
```

Then `_filter_new_entities()` and `_matches_previous_entity()` will still protect against duplicates.

In short: **keep masking for pipeline control, but give Qwen richer original context plus “already detected” span metadata.** This fixes context loss without breaking dedupe/redaction behavior.

Yes, it is good to check metrics after every document upload. But use the right type of metrics.

For each uploaded document, you usually **cannot calculate true accuracy / precision / recall**, because you do not have ground-truth labels for that document. The existing [test_metrics.py](./tests/test_metrics.py) is useful for offline benchmark testing, not per-upload production checks.

For every upload, you should track **pipeline health + quality warning metrics**.

Good per-document metrics for this codebase:

- `document_status`: `COMPLETED` / `FAILED`
- `workflow_stage` and `last_completed_stage`
- OCR/extraction confidence from `ocr_results.confidence_score`
- extracted text length
- total detected entities
- PII count / PHI count
- low-confidence entity count
- pending review count
- detector list used
- whether Qwen was invoked
- detector failures/skips
- duplicate/conflicting entity-type count
- redaction count vs entity count
- redacted file exists or not
- report generated or not
- processing duration

Important issue flags:

```text
OCR confidence too low
Extracted text empty
No entities found in a document with candidate-looking text
Too many low-confidence entities
Same span/value detected as different entity types
Qwen invoked too often
Qwen skipped while unresolved candidates remain
Redaction count != entity count
Redacted artifact missing
Report generation failed
Document stuck in PROCESSING
```

Your code already stores some of this in `reports`, `entities`, `confidence_scores`, `ocr_results`, and `processing_jobs`. But it does **not yet have a clean per-document “quality summary” metric layer**.

Best design would be to add a per-document quality check after report generation, something like:

```text
Document uploaded
-> OCR
-> Detection
-> Review preparation
-> Redaction
-> Report
-> Quality metrics / issue flags
```

So yes: checking metrics after every upload is a good idea. Just don’t call them “accuracy metrics” unless you have ground truth. Call them **pipeline health metrics** or **document quality metrics**.
